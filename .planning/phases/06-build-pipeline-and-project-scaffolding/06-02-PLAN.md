<objective>
Build the two pure-logic packages the scaffolder is built on: `slug` (canonical identifier
derivation + strict validation) and `detect` (T3 vs non-T3 project detection, Dockerfile
inspection, router-type detection). Both are deterministic input→output functions, so this is
a dedicated TDD plan — write the failing tests from the RESEARCH cases first, then implement.

Purpose: The slug is the single value that drives image name, namespace, host, and gitops dir,
so its validation is a security control (threat T-06-07, slug/path injection — reject before any
write). Detection implements SCAF-06: T3 apps get a generated Dockerfile + health route, while
non-T3 containers keep their own Dockerfile (never overwritten) and get a TCP probe.

Output: `internal/slug` and `internal/detect` with full unit coverage and testdata fixtures.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| operator CLI args (--slug/--port/--dockerfile) → filesystem/manifest writes | untrusted operator input validated before any path or manifest is written |
| app-repo files (package.json/Dockerfile) → scaffolder logic | repo contents parsed read-only; never mutated |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-06-07 | Tampering | slug.Validate / path derivation | high | mitigate | Strict regex `^[a-z][a-z0-9-]{1,30}$`; reject before any file write; --slug override validated identically (RESEARCH ## Security Domain V5) |
| T-06-09 | Tampering | detect.Detect (non-T3 Dockerfile) | medium | mitigate | Detection is read-only; SCAF-06 hard rule — never overwrite an existing Dockerfile; --dockerfile/--port validated |
| T-06-10 | Denial of Service | package.json/Dockerfile parsing | low | accept | Line-based tolerant parsing on local repo files the operator already trusts; no network input |
</threat_model>
