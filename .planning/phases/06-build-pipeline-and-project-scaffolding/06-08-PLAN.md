<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| operator GitHub account → CI/GitOps tokens | the two least-privilege tokens are minted here; scope creep = blast radius |
| CI runner → gitops-homelab (bump) | GITOPS_PUSH_TOKEN (fine-grained, Contents:write, gitops-homelab only) |
| kubelet → GHCR (private pull) | classic read:packages token inside the SOPS pull-secret |
| dev-box fixtures → scaffolder | offline fixtures exercise generation with a DUMMY token; no real secret written |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-06-01 | Elevation of Privilege | GITOPS_PUSH_TOKEN scope | high | mitigate | Checkpoint instructs a fine-grained PAT scoped to tkayage/gitops-homelab Contents:write only (or a deploy key if org policy blocks FG-PATs) |
| T-06-05 | Information Disclosure | GHCR package visibility | high | mitigate | Checkpoint requires confirming the package is Private; the pull path uses read:packages only |
| T-06-19 | Information Disclosure | dummy vs real token in fixtures | medium | mitigate | scaffold-verify.sh uses a clearly-dummy pull token and a scratch bare gitops repo; no real credential is generated, encrypted-to-git, or logged offline |
| T-06-03 | Tampering | generated workflow action pins | high | mitigate | Checkpoint step 4 has the operator confirm every generated action is pinned to a full commit SHA |
</threat_model>
